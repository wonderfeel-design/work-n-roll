Field Voice architecture

A farmer logs field work by Telegram voice note in English, Russian, Catalan or Spanish. The bot transcribes it, Gemma 4 turns it into a record, a rule-based judge scores it, and the farmer confirms it. An agronomist reviews and corrects records on a web console, asks questions by voice, and downloads the Excel log. Every process reads and writes one PostgreSQL database.

How a request moves

Four flows

ALog an activity

  1. /start asks the farmer's name; /help lists parcels and what the bot does.
  2. Voice note to the bot; Scribe returns text and language.
  3. Gemma 4 maps spoken names to parcels and returns one record per activity, with dates resolved in Europe/Madrid.
  4. Missing parcel, date, product or quantity: up to two questions, nothing saved yet.
  5. The card comes back in the farmer's language, as text and voice, and the draft appears in the console.
  6. ✅: the judge scores dose, crop and date; auto-approved or needs review.
Scribe ~1 s · Gemma up to 3 tries × 30 s

BCorrect a record

  1. Farmer: ✏️ on the card, then says the fix ("it was 14, not 40"); Gemma finds the changed field.
  2. Agronomist: Needs review, Correct, one field, a new value and a required reason.
  3. The value and a corrections row are written in one transaction.
  4. Within 10 s the bot tells the farmer what the agronomist changed.
  5. The next extraction prompt includes the correction as an example.

CExcel report

  1. Download report in the console. The bot's /report is not built yet.
  2. The sample workbook is the template: same tabs, colours and dropdowns.
  3. Lookups and dose per hectare stay live formulas.

DAsk by voice

  1. Tap the orb and ask; a pause ends the question.
  2. Scribe transcribes; the server computes totals and averages in Python.
  3. Gemini Flash phrases the answer; TTS speaks it in the chosen voice with subtitles.
  4. It listens again for a follow-up.
~3 s from question to answer

Why it looks like this

Decisions behind the diagrams

  • One transcript, then a read-back. Gemma 4 on the Gemini API has no audio input, so Scribe hears the note and the farmer confirms every record.
  • PostgreSQL instead of SQLite. A file database only worked while bot and console ran on one machine; Person 1's records never reached the console.
  • Strict corrections. Corrections train the judge, so the database enforces them: foreign key to the record, required reason, append-only, no deleted records.
  • Gemini Flash for spoken answers. Gemma 4 thinks 12–18 s before every answer on this API, which is too slow for a conversation; it still does all extraction.
  • Numbers from Python, words from the model. The assistant gets precomputed totals, so arithmetic is exact and the model can't change data.
  • Polling, not live push. The console asks every 2 s; it looks the same in a demo and needs no extra server pieces.
